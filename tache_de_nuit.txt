## BUGS CONNUS À CORRIGER (P0)

1. AFFICHAGE TRONQUÉ : un TextBox/TextLabel Roblox est limité à ~16 000 caractères ; un gros script
   s'affiche coupé. Ne JAMAIS mettre une grosse réponse dans un seul élément. Découpe en plusieurs
   éléments (≤ 8000 caractères, coupés aux sauts de ligne, ligne géante coupée aussi) dans un
   ScrollingFrame + UIListLayout. Pour les blocs de code longs : affichage complet réparti en
   morceaux ET bouton pour replier/déplier (aperçu 30 lignes par défaut, "Tout afficher").
2. TEXTE NON COPIABLE : un TextLabel n'est pas sélectionnable et les plugins n'ont PAS d'accès au
   presse-papier. Solutions à combiner :
   - tout texte affiché utilise des TextBox `TextEditable=false`, `ClearTextOnFocus=false`
     (sélectionnable à la souris, Ctrl+C fonctionne) ;
   - chaque bloc de code a des boutons : "Sélectionner tout" (CaptureFocus + SelectionStart/CursorPosition),
     "Injecter", "Ouvrir dans l'éditeur", "Copier via éditeur" (crée/ouvre un script temporaire
     contenant le code pour faire Ctrl+A / Ctrl+C) ;
   - n'appelle JAMAIS `StudioService:CopyToClipboard` (n'existe pas).
3. INJECTION DANS LE SCRIPT EXISTANT : après une réponse contenant du code, proposer un bouton
   d'injection qui cible correctement : script sélectionné → on l'écrase ; objet sélectionné
   contenant exactement un script → on écrase celui-là ; plusieurs scripts → l'utilisateur choisit
   dans une petite liste ; aucun → nouveau Script (type adapté : Script/LocalScript/ModuleScript
   selon le contenu et la demande) au bon endroit (ServerScriptService, StarterPlayerScripts,
   enfant de l'objet sélectionné…). Écriture via `ScriptEditorService:UpdateSourceAsync`
   (fallback `.Source`). Avant injection : vérification syntaxique via `loadstring` SANS l'exécuter
   (compile seulement), avertissement si le code semble tronqué, option "voir le diff" (lignes
   ajoutées/supprimées). Toujours un waypoint ChangeHistory + bouton Annuler fiable.
   Utiliser si possible `ChangeHistoryService:TryBeginRecording/FinishRecording`, sinon SetWaypoint.
4. `extractCode` doit gérer : ```lua, ```luau, ``` seul, `\r\n`, bloc jamais refermé (réponse coupée),
   plusieurs blocs (proposer chaque bloc séparément avec sa cible, pas seulement le plus gros).
   Le modèle peut indiquer le fichier cible dans une ligne `-- FICHIER: game.ServerScriptService.X`
   juste avant/dans le bloc : le parser doit l'utiliser.
5. `getObjectFromPath` est définie APRÈS son premier usage (variable nil dans le handler
   `provideContextButton`) : réorganiser pour que toutes les fonctions soient définies avant usage.
   Réécrire la résolution de chemin pour supporter les noms contenant des points/espaces et les
   doublons de noms (format de chemin non ambigu, ex. tableau JSON de segments, ou `game.Workspace["Mon Objet"]`,
   avec suffixe d'index si doublon).
6. Le code généré par `Instance.new("Script")` + `.Source = [[...]]` casse si le code contient `]]`.
   Ne plus s'appuyer sur ça : voir outils `write_script` / `create_instance`.
7. Serveur : `requests.post` sans timeout, `/api/cancel` ne stoppe pas réellement Ollama, `ollama_payload`
   inutilisé, indentation mixte tabs/espaces, aucune option `num_ctx`/`num_predict` (→ réponses COUPÉES),
   mémoire des tâches qui grossit sans fin, `print` du prompt entier. Corriger tout ça.

## ARCHITECTURE CIBLE : AGENT À OUTILS (P1, cœur du projet)

### Boucle d'agent
Le plugin envoie la demande ; le modèle répond soit par du texte final, soit par UN appel d'outil ;
le plugin exécute l'outil localement, renvoie le résultat au modèle ; on boucle (max 12 itérations,
bouton Stop, compteur visible). Le serveur gère l'historique de conversation (liste de messages par
`session_id`) et utilise `/api/chat` d'Ollama (pas `/api/generate`). Bouton "Nouvelle conversation".
Historique persistant (plugin:SetSetting, taille limitée).

### Protocole d'outils (robuste, indépendant du modèle)
Le prompt système (côté serveur) décrit les outils et impose : pour appeler un outil, répondre par UN
SEUL bloc ```json {"tool": "...", "args": {...}} ``` et RIEN d'autre ; pour répondre à l'utilisateur,
texte normal. Le serveur/plugin parse de façon tolérante (JSON entouré de texte, guillemets typographiques,
virgules traînantes, fences ```json ou non), détecte le function-calling natif d'Ollama si le modèle le
supporte (`tools` dans /api/chat) mais ne dépend pas de lui. Si le JSON est invalide : renvoyer au modèle
un message d'erreur précis et laisser 2 retries.

### Outils à implémenter côté plugin (toutes les écritures sous waypoint + annulables)
LECTURE (les yeux) :
- `get_selection` : chemins, classes, propriétés clés des objets sélectionnés.
- `get_tree` {root?, depth?, max_nodes?} : arborescence du workspace/services avec Nom, Classe,
  nombre d'enfants, tronquée proprement (max ~300 nœuds, message "… N autres") ; défaut = vue
  d'ensemble des services utiles (Workspace, ServerScriptService, ReplicatedStorage, StarterGui,
  StarterPlayer, ServerStorage, Lighting, SoundService).
- `find_instances` {name?, class?, root?, limit?} : recherche.
- `get_properties` {path, names?} : propriétés lisibles (utiliser `ReflectionService` si disponible
  sinon une liste curée par classe : BasePart, Model, Humanoid, Light, GuiObject, Sound, Attachment,
  Script…), + Attributes + Tags (CollectionService). Sérialiser Vector3/Color3/CFrame/UDim2/EnumItem/
  BrickColor/Instance-ref de façon réversible (voir "Sérialisation").
- `read_script` {path, from_line?, to_line?} : source numérotée, avec pagination pour les gros scripts.
- `search_code` {query, root?} : grep dans les Sources de tous les scripts (retourne chemin + n° de ligne + extrait).
- `get_output` {last_n?} : dernières lignes de LogService (erreurs/warnings/prints), capturées en
  continu via `LogService.MessageOut` dans un buffer circulaire (500 lignes).
- `get_script_errors` : erreurs de syntaxe/analyse si accessibles (ScriptEditorService diagnostics, à vérifier).
ÉCRITURE (les mains) :
- `create_instance` {class, parent, name?, properties?} : propriétés en JSON typé ; vérifie que la
  classe est créable (`pcall(Instance.new)`), que le parent existe, refuse les classes dangereuses
  inutiles ; renvoie le chemin créé. Supporte la création en lot : `create_instances` [{...}] avec
  hiérarchie imbriquée (children) pour construire des objets complexes (porte, flaque, tour, PNJ, GUI…)
  en un seul appel.
- `set_properties` {path, properties}, `set_attributes`, `add_tag`.
- `delete_instance` {path} : demande une CONFIRMATION utilisateur (bouton dans l'UI) si > 1 objet ou
  si c'est un script/modèle ; jamais de suppression de services ni de `game`.
- `clone_instance`, `move_instance` (reparent), `group_as_model`.
- `write_script` {path | parent+name+class, source, mode: "replace"|"create"|"append"|"patch"} :
  écrit un script complet sans passer par du code exécuté. Mode "patch" = {search, replace} appliqué
  de façon unique sur la source (évite de réécrire 800 lignes pour 3 lignes).
  Avant écriture : compile-check, diff affiché, bouton Annuler.
- `run_code` {code} : exécute du Luau dans le contexte plugin (loadstring) avec timeout non bloquant
  (déjà présent : le conserver et l'améliorer), tracking des instances créées, capture des erreurs,
  cap sur le nombre d'instances créées (ex. 2000) ; ce n'est qu'un échappatoire quand les outils
  structurés ne suffisent pas. Utiliser un environnement avec `print` redirigé vers le buffer de sortie.
- `insert_asset` {asset_id, parent?} via `InsertService:LoadAsset` (pcall, erreurs claires : asset
  privé, ID invalide) ; ne PAS dépendre d'une recherche Toolbox (API non fiable) : si l'utilisateur
  demande un objet sans ID, le construire à partir de primitives avec `create_instances`
  (Part, WedgePart, Cylinder via Shape, UnionOperation interdit, MeshPart seulement si MeshId fourni).
- `select_instances` {paths} et `focus_camera` {path} (si possible, via workspace.CurrentCamera / `Selection`).
Chaque outil renvoie au modèle un résultat COURT et structuré (JSON compact), tronqué si > ~6000
caractères avec indication de pagination.

### Sérialisation de valeurs (module pur, testé)
Format JSON typé, ex. : `{"Vector3":[1,2,3]}`, `{"Color3":[255,0,0]}` ou `"#FF0000"`,
`{"CFrame":[x,y,z]}` ou position+rotation en degrés, `{"UDim2":[sx,ox,sy,oy]}`, `{"Enum":"Material.Neon"}`,
`{"BrickColor":"Bright red"}`, `{"Instance":"<chemin>"}`, nombres/chaînes/booléens bruts. Fonctions
`decodeValue(typeHint, json)` / `encodeValue(value)`. Types de propriété déduits par la valeur actuelle
ou via reflection. Erreurs explicites ("Propriété X inexistante sur Part").

### Contexte automatique (yeux par défaut)
À chaque demande, le plugin joint un contexte COMPACT et budgété (limite en caractères configurable) :
sélection (chemins + classes + sources des scripts sélectionnés, tronquées avec pagination), script
ouvert dans l'éditeur, résumé du projet (arbre de scripts + nombre d'objets par service), dernières
erreurs de la console. Le modèle utilise ensuite les outils pour creuser. Remplace l'ancien système
`[LIRE_FICHIER: ...]` par l'outil `read_script` (appelé automatiquement, plus besoin du bouton
"Fournir le fichier" — le retirer proprement).

## SERVEUR PYTHON (P1)

- Passer à `/api/chat` d'Ollama avec historique par `session_id` ; nouveaux endpoints :
  `POST /api/agent` (message + session_id + model + mode), `GET /api/status/<id>`,

  `GET /api/models` (via Ollama `/api/tags`), `GET /api/health`.
- Streaming : stocker le texte partiel dans la tâche (`partial`) pour que le plugin affiche la réponse

- Options Ollama configurables : `num_ctx` (défaut 16384, max selon modèle), `num_predict` (défaut
  -1 ou 8192), `temperature` (0.2 pour code), `keep_alive`. Détecter `done_reason == "length"` et
  renvoyer `truncated: true` ; le plugin propose alors "Continuer" (envoie "continue exactement où
  tu t'es arrêté") et recolle les morceaux.
- Nettoyage `<think>...</think>` conservé (et variantes), mais aussi retirer proprement les blocs
  de raisonnement non fermés.
- Prompts système par mode, réécrits et solides, en français, qui expliquent : l'environnement
  (Roblox Studio, plugin), le protocole d'outils, les bonnes pratiques Luau (task.wait, pas de wait(),
  RemoteEvents, FilterEnabled, éviter les boucles infinies sans yield), le format de réponse
  (toujours des blocs ```lua complets avec `-- FICHIER:` cible ; pas de "// reste du code inchangé"
  quand on remplace un script entier ; sinon utiliser `write_script` mode patch), et la règle
  "ne jamais inventer un chemin : utilise get_tree/find_instances d'abord". Modes : Assistant,
  Constructeur, Codeur Strict, Débogueur, Agent Autonome (planification puis exécution par outils).
- Robustesse : timeouts (connexion 10 s, lecture longue configurable), gestion des erreurs Ollama
  (modèle absent, Ollama éteint → message clair renvoyé au plugin), nettoyage des tâches > 1 h,
  verrou thread-safe sur `memoire_taches`, logs concis (tronquer les prompts affichés), config via
  variables d'environnement (OLLAMA_URL, PORT), `requirements.txt`.
- Tests pytest avec Ollama mocké : création de tâche, statut, annulation, troncature, nettoyage think.

## QUALITÉ / SÉCURITÉ (P2-P3)

- Boucle d'auto-correction : après une écriture de script ou un run_code, lire la console pendant
  ~2 s, et si erreur de syntaxe/exécution, la renvoyer au modèle automatiquement.
- Garde-fous : jamais de `game:Destroy()`, pas de suppression de services, plafond sur le nombre
  d'objets créés par appel, pas d'appels HTTP depuis le code généré sans demande explicite, aucun
  envoi de données hors du réseau local (le serveur n'appelle que Ollama).
- Journal des actions (table en mémoire + affichage) et export du journal dans un StringValue/Script
  de notes si l'utilisateur le demande.
- Performance : ne jamais parcourir `game:GetDescendants()` entier de façon répétée ; limiter, mettre
  en cache avec invalidation sur DescendantAdded/Removing, utiliser task.wait() régulier dans les
  longues boucles pour ne pas geler Studio.
- Gérer les cas limites : script ouvert mais non sélectionné, sélection multiple, objets supprimés
  entre-temps, scripts désactivés (Enabled=false) signalés mais lisibles, Studio en mode Play/Run.
- Compatibilité : aucune API dépréciée (`wait`, `spawn`, `delay`, `Instance.new(class, parent)`),
  utiliser `task.*`, `ScriptEditorService`, `Selection`, `ChangeHistoryService`.
